# Key Vault, Identity, and Secret Management

## Objective

The QA agent must use protected systems without exposing credentials to prompts, sub-agents, logs, browser evidence, or artifacts.

## Recommended architecture

```text
Human/Trigger
  -> Agent Gateway
  -> Workload Identity
  -> Policy Decision
  -> Credential Broker
  -> Secret Manager / Vault
  -> Short-lived credential or delegated token
  -> MCP server or adapter
```

The language model receives a capability handle such as `credential_lease_id`, never the secret value.

## Provider strategy

- **When hosted on Google Cloud:** use Google Secret Manager with Workload Identity Federation or native workload identity; avoid service-account key files.
- **When hosted on Azure:** use Azure Key Vault with managed identities and Azure RBAC/PIM.
- **For multi-cloud or dynamic PostgreSQL credentials:** consider HashiCorp Vault database secrets with short leases and revocation.
- **When another enterprise vault already exists:** implement the same `SecretProvider` interface and preserve the controls below.

## Secret categories

| Category | Examples | Recommended handling |
|---|---|---|
| OAuth client material | Atlassian, Microsoft | Vault; rotation; admin ownership |
| Delegated refresh tokens | Jira/Teams user delegation | Encrypted token store; user/revocation binding |
| Repository tokens | Bitbucket API/access tokens | Scoped per workspace/project; short expiry where possible |
| Database credentials | Read-only and test-data roles | Dynamic credentials or short-lived rotation |
| API client credentials | Internal services | Workload identity preferred; otherwise scoped secret |
| Browser test accounts | Username/password or federation | Dedicated identity; automatic rotation; no human reuse |
| Signing/encryption keys | Artifact URLs, evidence signatures | Managed key service/HSM; never export private keys |
| Webhook secrets | Jira/Bitbucket/CI events | Separate per source and environment; rotation overlap |

## Naming convention

```text
qa-agent/<organization>/<project>/<environment>/<system>/<identity>/<credential>
```

Examples of references, not values:

```text
qa-agent/acme/PCC/qa/jira/reader/oauth
qa-agent/acme/SOP/playground/product/browser-user
qa-agent/acme/DataBridge/qa/postgres/readonly
```

## Mandatory controls

1. Prefer workload identity over stored long-lived credentials.
2. Issue per-project, per-environment, per-system identities.
3. Separate read and write identities.
4. Use short-lived credentials and revoke them when a run finishes.
5. Enforce least privilege in the destination system, not only in the agent platform.
6. Record secret metadata access without logging values.
7. Rotate on schedule and immediately after suspected exposure.
8. Deny secrets in environment dumps, exceptions, traces, screenshots, model inputs, and artifacts.
9. Use just-in-time privileged access for administrators.
10. Require two-person approval for production credential grants.
11. Scan source, config, artifacts, and logs for leaked credentials.
12. Maintain break-glass credentials outside normal agent paths and test the process.

## Credential lease contract

```yaml
lease_id: lease-uuid
principal: qa-db-reader-PCC-qa
project: PCC
environment: qa
system: postgres
allowed_actions:
  - schema.read
  - query.execute_readonly
expires_at: 2026-08-06T02:30:00Z
max_uses: 20
approval_id: null
secret_value_visible_to_model: false
```

## Prohibited patterns

- Shared `.env` files containing organization credentials.
- One Bitbucket, Jira, database, or Teams token reused across projects and environments.
- Raw secrets stored in agent memory, vector indexes, conversation history, or test evidence.
- Secrets passed as MCP tool arguments generated by the model.
- Production database passwords provided to browser or general-purpose agents.
- Permanent write credentials attached to the supervisor.
